## 1. Purpose

Establish the reporting and exception-management layer following B.6.23. The framework converts collected control evidence into structured governance reports, tracks exceptions to closure, and ensures material risks are escalated to the authorized authority.

This document is a planning/control framework only. It does not claim live production evidence, compliance, or approval.

## 2. Reporting cycle

Each governance cycle should produce a report covering:

- control reviews completed;
- evidence collected;
- open findings and exceptions;
- security/privacy events;
- production changes;
- backup and recovery status;
- access/privilege changes;
- overdue corrective actions;
- re-authorization triggers;
- decisions requiring management or committee action.

The report must clearly distinguish **PASS/OBSERVED**, **PENDING**, **FAILED**, and **NOT APPLICABLE** states.

## 3. Exception register

Each exception should have:

| Field | Requirement |
|---|---|
| Exception ID | Unique reference |
| Control domain | Security/privacy/data/operations/etc. |
| Description | Evidence-based statement |
| Severity | Based on documented impact |
| Date detected | Required |
| Owner | Authorized responsible role |
| Immediate control | Mitigation where required |
| Corrective action | Defined remediation |
| Target date | Required |
| Re-test evidence | Required before closure |
| Approval/disposition | Authorized decision |
| Closure date | Required on closure |
| Status | OPEN / MITIGATED / CLOSED / ESCALATED |

## 4. Escalation rules

### Critical
Immediately escalate and activate the applicable incident/security response process. Affected functionality may be restricted where necessary to protect users, data or system integrity.

### High
Assign an owner promptly, define mitigation and track to prioritized remediation and re-test.

### Medium / Low
Track through the approved corrective-action process with documented ownership and target dates.

Severity must be supported by evidence; labels must not be used as substitutes for investigation.

## 5. Corrective-action lifecycle

**Detect → Record → Assess → Contain/Mitigate → Remediate → Re-test → Approve → Close → Trend Review**

An exception cannot be closed merely because remediation was attempted. Closure requires evidence that the control requirement is satisfied or that an authorized residual-risk decision has been recorded.

## 6. Residual-risk handling

Where a finding cannot immediately be eliminated, the authorized authority may record a time-bound residual-risk decision containing:

- affected control;
- documented risk;
- temporary mitigation;
- responsible owner;
- expiry/review date;
- approving authority;
- follow-up action.

Residual-risk acceptance must never be assumed from silence or from an expired target date.

## 7. Governance dashboard fields

A periodic dashboard may summarize, without exposing confidential information:

- controls reviewed;
- evidence items collected;
- open critical/high/medium/low exceptions;
- overdue actions;
- incidents by status;
- changes reviewed;
- backup/restore test status;
- re-authorization items;
- upcoming review dates.

Do not publish confidential production evidence or personal data in the public repository.

## 8. Management review

Management/authorized governance review should confirm:

1. significant exceptions are visible;
2. ownership is assigned;
3. overdue actions are escalated;
4. residual risks have explicit approval where applicable;
5. material changes have triggered the required review;
6. closure evidence is sufficient;
7. next review dates are scheduled.

## 9. No-go conditions

Do not report a control domain as fully closed when mandatory evidence is absent, a critical exception remains unresolved without authorized control, or a required approval is missing.
